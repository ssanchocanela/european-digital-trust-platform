# EUDI ecosystem sandbox — milestone plan

- **Status:** DRAFT for the S1 checkpoint, 12 November 2026.
- **Implements:** [`specification.md`](specification.md), [ADR 0014](../adr/0014-sandbox-trust-domain.md),
  [ADR 0015](../adr/0015-sandbox-sign-in-by-pid.md).

Each milestone:
- runs on its own branch from the previous one;
- ends with a PR and a **STOP**;
- commits in small steps;
- keeps `pnpm verify` green;
- adds adapter tests in the separately skippable suite.

A milestone that needs a phone, a wallet build or a deployment ends with the manual steps written and
the result recorded honestly (CLAUDE.md §8), never simulated.

## S2 — Foundations

**Before any code — three readings and two decisions:**
1. Read EN 319 412-1 §5.1.3/§5.1.4, EN 319 411-1 §6.6.1–6.6.3, EN 319 412-2/-3 and TS 119 182-1.
   Close Q-S1, Q-S2 and Q-S4 of the specification with clause citations.
2. **User decision — Q-S6:** the cryptographic library for X.509 and CRL issuance. The candidates are
   assessed in a short note: maintenance, licence, supply chain, P-256 and CRL support.
3. **User decision — Q-S7:** the sandbox policy OID arc.

**Then build:**
- `packages/sandbox-domain`: organisation, person, membership, invitation, session, with the state
  rules and their unit tests.
- Persistence and migrations for them, up from an empty database.
- **Sign-up and sign-in by PID** (ADR 0015):
  - the sign-in verifier as a platform-operated Relying Party Instance;
  - the fixed anchor set with its start-up check;
  - the HMAC subject;
  - `__Host-` sessions;
  - a test that a PID under a participant anchor is refused.
- Owner/member roles, invitations, organisation API keys; cross-organisation isolation tests.
- **Engine credentials in the database**, encrypted at rest; runtime engine-tenant creation with every
  role (G-6). The existing environment variable keeps working.
- `packages/sandbox-pki` skeleton:
  - the key-store port;
  - the domain's seven roots and signers generated by a script, never committed;
  - the `TEST` guard: refuse to start in `PRODUCTION`.
- `apps/sandbox-portal` skeleton: first screen, sign-up, sign-in, organisation, members.

**Records:**
- the TS 119 475 inconsistencies and the TS5 entitlement-URI inconsistency, in `interop-findings.md`;
- the CA key limitation, in `security-limitations.md`.

**Done when:** a person signs up with a PID from the sandbox wallet, as a real run on the local stack
(SAME_DEVICE through the test-session gateway); a second person is invited and signs in; isolation
tests pass.

**State, 12 November 2026 — built, not yet run with a wallet.** Everything above is implemented and
tested (unit 531, integration 152). The readings closed Q-S1, Q-S2 and Q-S4; the user decided Q-S6
(own DER encoder) and Q-S7 (`2.25.…`). Two corrections to the plan:
- the real run uses an **existing** test wallet (W8/W9) and the development Access CA, because the
  sandbox CA issues nothing before S3 and no sandbox wallet build exists yet;
- it is **cross-device** from a laptop, because the portal is not exposed before S6.

Both are in [`s2-run-sheet.md`](s2-run-sheet.md), which also lists what to record. ADR 0015 was
amended on the way (Decision 3 and 4: the subject's basis and the typed display name).

## S3 — Certificate service

- **WRPAC issuance** per specification §7.1:
  - hosted (key to the engine) and take-away (CSR);
  - variants AC-00..AC-06 (AC-07 only if S2 found its rule);
  - CRL publication and revocation.
- **WRPRC issuance** per §7.2: variants RC-00..RC-13, the Token Status List, revocation.
- **Port the compliance guard** from edt-pid-connector's `Wrprc.kt`, so the portal warns when a
  policy over-asks — except under RC-08, where over-asking is the point.
- **Port the WRPAC and WRPRC validators.** The sandbox validates every certificate it issues and
  reports which checks a defective one fails, as a self-test of the catalogue.
- **The three LoTEs**, built and signed on change and daily; history kept.
- **TS5 register read API**, JWS-signed by the Registrar.
- Portal: services, intended uses, certificates, variants, downloads.
- Q-S5 answered from the Wallet Core source.

**Done when:** every variant is issued and its self-test fails exactly the check the catalogue names;
the lists verify with the existing LoTE verifier; the register answers for a test organisation.

## S4 — The Relying Party role

- Hosted verifier provisioning with the participant's certificates, on a runtime engine tenant; the
  WRPRC sent as `verifier_info` (and withheld for RC-01).
- Presentation policies under intended uses; presentations `SAME_DEVICE`, `QR` under ADR 0012.
- **Run reports**, with the tester's observation form.
- **The sandbox wallet build** (`build.sh --profile sandbox`), its deviations registered.
- **Real runs**, recorded in `docs/sandbox/runs.md`:
  - AC-00 + RC-00;
  - then every variant with the sandbox build;
  - *Check Registration Certificates* **off and on**, and both results reported.

**Done when:** those runs are recorded, each with its wallet build, deviations and preference
position, and nothing in them is described as more than it is.

## S5 — The PID Provider role

- Sandbox PID CA issuing participants' signing certificates (PID-00..PID-02).
- Hosted PID issuer per participant on a runtime engine tenant.
- The synthetic-values issuance form; offers by link and QR; PID revocation (PID-03).
- Issuance-side WRPRC variants as take-away only, with the G-10 statement.
- **An ADR on signing issuer metadata in front of the engine** (gate (a)): assessment and decision.
  Implementing it is a later milestone if accepted.
- **Real runs:** issue from a participant's hosted issuer to the sandbox wallet, then present that PID
  to another participant's hosted verifier, with *Check Registration Certificates* in both positions.

**Done when:** that closed loop is recorded.
