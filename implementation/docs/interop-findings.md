# Interoperability findings

Divergences between EUDIPLO or the EUDI Reference Implementation and ARF 3.0.0 / the Technical
Specifications, and divergences between an implementation's documentation and its code.

Per the implementation rules, a divergence is recorded here and the platform domain model is **not**
bent to match an implementation quirk.

Sources pinned as in [`phase-0-findings.md`](phase-0-findings.md) §1.

Status values: `OPEN` (unresolved), `ACCEPTED` (we work around it), `INFORMATIONAL` (no action).

---

## A. EUDIPLO v7.6.0 — documentation vs code

These matter because the adapter must be written against the code and the OpenAPI document, not
the prose.

| # | Documented | Actual (verified in source at `3b2a9e7`) | Status |
|---|---|---|---|
| A1 | `POST /clients` (example in `administration/authentication.md`) | `POST /client` — `ClientController` is `@Controller("client")` | `ACCEPTED` |
| A2 | `PATCH /{tenant}/status-management/status-list/{listId}/entry/{index}` with `{value}` (`issuance/status-management.md`) | **No such route.** The only exposed status mutation is `POST /session/revoke` with `{sessionId, credentialConfigurationId?, status: 0\|1\|2}`. `PATCH /status-lists/:listId` updates list *configuration*, not entries | `ACCEPTED` — the adapter uses `POST /session/revoke` |
| A3 | `/{tenant}/chained-as/par\|authorize\|callback\|token` and `/{tenant}/chained-as/.well-known/*` (`architecture/authorization.md`) | `/issuers/:tenantId/chained-as/*`; metadata at `/.well-known/oauth-authorization-server/issuers/:tenantId/chained-as` | `ACCEPTED` |
| A4 | `{"sessionConfig": {"cleanupMode": "anonymize", "retentionDays": 90}}`, `cleanupMode: "delete" \| "anonymize"` (`architecture/sessions.md`) | `{ttlSeconds (int, min 60, nullable), cleanupMode: "full" \| "anonymize"}`. Defaults `SESSION_TTL=86400`, `SESSION_CLEANUP_MODE=full`, `SESSION_TIDY_UP_INTERVAL=3600`. There is no `retentionDays` and no `delete` value | `ACCEPTED` — the retention decision in ADR 0004 uses the real fields |
| A5 | `docker run … ghcr.io/openwallet-foundation-labs/eudiplo:latest` (`reference/wallet-compatibility.md`) | Images publish to `ghcr.io/openwallet-foundation/eudiplo` (the `-labs` org prefix is stale) | `INFORMATIONAL` |
| A6 | "OAuth Token Status List specification (**RFC 9528**)" (`issuance/status-management.md`) | RFC 9528 is not the Token Status List. `reference/protocols.md` links the correct `draft-ietf-oauth-status-list`, and the dependency is `@owf/token-status-list` ^0.3.2 | `INFORMATIONAL` — cite the IETF draft, never RFC 9528 |
| A7 | `architecture/sessions.md` shows anonymization nulling `credentialClaims` and `presentedCredentials` | The entity fields are `credentialPayload` and `credentials` | `INFORMATIONAL` |
| A9 | **The engine's migrations do not create its schema; TypeORM `synchronize` does.** On a fresh database the v7.6.0 image logs `[Migration] Fresh database detected. Schema will be created by TypeORM synchronize.` and `[Migration] Ensure DB_SYNCHRONIZE=true is set for initial setup.`, after which **every** migration skips with "table not found". With `DB_SYNCHRONIZE=false` the engine then crash-loops at bootstrap on `QueryFailedError: relation "client_entity" does not exist` (PostgreSQL `42P01`), from `InternalClientsProvider.onApplicationBootstrap` | `BLOCKING` until configured, and it **inverts the platform's own rule**. `docker-compose.yml` had `DB_SYNCHRONIZE: "false"` on principle — the platform uses explicit migrations and no auto-synchronisation. The engine gives no alternative, so it is now `${ENGINE_DB_SYNCHRONIZE:-true}` with the evidence quoted inline. This is confined to the **engine's** database, which is a separate PostgreSQL instance precisely so the engine's schema management cannot reach the platform's (ADR 0001, ADR 0004). The platform's own database still has no auto-synchronisation anywhere. Found by running the stack on 11 September 2026 |
| A10 | **Every management route is under `/api`; the documented paths omit it.** The engine serves two OpenAPI documents on one port: the wallet-facing *Protocol API* at `/docs-json`, whose routes are unprefixed, and the *Management API* at `/api/docs-json`, whose routes are all prefixed. So the real paths are `PUT /api/session-config`, `POST /api/verifier/config`, `POST /api/verifier/offer`, `GET,DELETE /api/session/{id}`, `POST /api/key-chain/import` — while `GET /health` belongs to the protocol document and is genuinely unprefixed | **A real adapter defect, now fixed.** The adapter had the correct path only for `POST /api/oauth2/token` and `/health`, which is exactly why authentication and the health check passed while every other call returned `404`. The prefix is now applied centrally in `EngineClient.request` as `MANAGEMENT_PREFIX`, and a path that already carries it is rejected rather than silently doubled into `/api/api/...`. Caught by the adapter-contract suite the first time it ran against a real container |
| A11 | **The bootstrap `root` client cannot serve a Relying Party Instance.** Its token carries `roles: ["tenants:manage"]` and **`tenant_id: null`**: it is a tenant-*management* credential and is refused on every tenant-scoped route. A usable credential comes from `POST /api/tenant`, which returns a per-tenant admin client (`{id}-admin` plus a generated secret) whose token carries the real `tenant_id` and the `presentation:manage` / `presentation:request` roles | **A documentation defect in this repository, now fixed.** `.env.example` shipped `ENGINE_TENANT_CREDENTIALS=root=root:<secret>` as the bootstrap entry, which can never complete a presentation flow. It also **confirms ADR 0002 Decision 3 empirically**: the engine's own model requires one client per tenant, and the platform maps one engine tenant to one Relying Party Instance. Found when the adapter suite's `404`s became `401`s |

## B. EUDIPLO vs ARF 3.0.0 / TS

| # | Finding | Citation | Status |
|---|---|---|---|
| B1 | **Revocation is reversible in EUDIPLO.** `POST /session/revoke` accepts `status: 0` (valid) after `status: 1` (revoked). ARF requires that a revocation SHALL NOT be reversed | `AS-AP-07-007` (`VCR_04`) | `OPEN` — the **platform** must reject un-revocation while still permitting reinstatement from *suspended* (`status: 2` → `0`). Enforced in the platform lifecycle, not in the engine |
| B2 | **mdoc status mechanism unverified.** ARF requires the Attestation Status List or Attestation Revocation List mechanism of Annex 2 of the amended CIR 2024/2979 for mdoc. EUDIPLO implements the IETF Token Status List (JWT and CWT encodings). Whether the CWT encoding satisfies that Annex is not established | `AS-AP-07-019` (`VCR_11`) vs `AS-AP-07-020` (`VCR_11a`) | `OPEN` — open question Q4. Not on the V0 path (V0 issues SD-JWT VC, covered by `VCR_11a`). **Must not be claimed for mdoc** |
| B3 | **Trust anchor *management* obligations are not met by caching alone.** EUDIPLO normalises ETSI TS 119 602 LoTEs and ETSI TS 119 612 Trusted Lists into one trust store and exposes cache controls, which satisfies the *shape* of `OIA_15b`. But `OIA_15a` obliges a Relying Party to download the latest lists, propagate added anchors to all Instances, and **remove** invalidated or expired anchors | `EW-PIO-01-029` (`OIA_15b`), `EW-PIO-01-028` (`OIA_15a`) | `OPEN` — a platform-owned trust-anchor management responsibility, not an engine feature. Out of V0 scope; must appear in `security-limitations.md` |
| B4 | **No signature on EUDIPLO's outbound webhooks.** Auth options are `apiKey`, `bearerToken`, `basic`, `none`; there is no payload signature, no timestamp and no event id. The `presentation.completed` payload carries `presentedClaims` | — (not an ARF requirement; a security property) | `ACCEPTED` — mitigated by internal-network-only delivery, a platform-side bearer secret, platform-side idempotency keyed on the EUDIPLO session id, and polling as the V0 default. The platform's own customer-facing webhook is HMAC-signed independently |
| B5 | **EUDIPLO persists presentation and issuance content** on the session row (`credentials: VerificationResult[]` including disclosed payloads; `credentialPayload` including inline issuance claims) for `SESSION_TTL`, default 24 h, purged by an hourly job | `AS-RP-01-002` (`OIA_16`) obliges the RP Instance to discard unique elements and timestamps as soon as they are no longer needed | `ACCEPTED` with mandatory configuration — see ADR 0004. Not a defect in EUDIPLO; a default that must be overridden |
| B6 | **`OIA_16` forbids propagating unique elements upward.** Salts, attribute hashes, the revocation index, the device-binding public key and the provider signature value must not be communicated to the Relying Party or anyone else. EUDIPLO's `VerificationResult` and `SessionOutcome.trust` expose `issuanceThumbprint` and `revocationThumbprint` | `AS-RP-01-002` (`OIA_16`), `AS-AP-10-064` (`ISSU_35`) | `ACCEPTED` — the platform's result policy must strip these from the **customer-facing** result, not only from storage |
| B7 | **EUDIPLO's RPRC check is narrower than `RPRC_21`.** EUDIPLO validates that every DCQL credential appears in the certificate's authorized `credentials` claim, and auto-derives `credentials` from `dcql_query.credentials` forwarding only `format`, `claims` and `meta`. `RPRC_21` is about the requested **attributes** being within the registered list | `EW-DM-44-027` (`RPRC_21`) | `INFORMATIONAL` — complementary, not contradictory. The platform's §6.1 claim-path subset check is the attribute-level layer and returns `422` at policy publication, before any wallet interaction |
| B8 | **`rpId` cannot be set per request.** EUDIPLO derives it automatically from the tenant's registrar relying party. Consistent with `Reg_32` (one EU-wide unique identifier per entity) but it constrains the tenant mapping | `AS-MS-27-043` (`Reg_32`), `EW-DM-44-013` (`RPRC_08`) | `ACCEPTED` — one EUDIPLO tenant per `RelyingPartyInstance`; see ADR 0002 |
| B9 | `readerAuth` (ISO 18013-7) "extracts the Access private key as a JWK, so KMS-backed non-extractable keys are not yet supported" | — | `INFORMATIONAL` — out of V0 scope (no proximity, no DC API), but it bears on any future HSM-backed deployment |
| B10 | Registrar credentials imported from `config/{tenant}/registrar.json` at startup are **not** validated, unlike those saved via the API | — | `INFORMATIONAL` — V0 does not use the registrar client (see §5.5 of the findings) |

## C. EUDI Reference Implementation vs ARF 3.0.0

| # | Finding | Citation | Status |
|---|---|---|---|
| C1 | **The dev environment collapses three ARF trust domains into one.** The seven trust anchors in `WRPACProviders.jwt`, `WRPRCProviders.jwt` and `PIDProviders.jwt` are byte-identical (same SHA-256 digests), and are certificates named `CN=PID Issuer CA 0x, O=EUDI Wallet Reference Implementation, C=EU` with CRLs under `https://preprod.pki.eudiw.dev/crl/`. ARF keeps PID Provider, Access CA and registration-certificate-provider trust strictly separate | ARF §3.18, §3.19; `AS-WP-06-005` (`RPA_04`); `EW-DM-44-005` (`RPRC_02a`); `EW-PIO-01-024` (`OIA_12`) | `INFORMATIONAL`, **with a design consequence**: the platform's `TrustResolver` must keep the domains separate and must never infer one from another, even though the reference environment would let it. Matches what [`06-shared-capabilities/trust-infrastructure.md`](../../06-shared-capabilities/trust-infrastructure.md) already requires |
| C2 | **Registration-certificate checking ships off** in the RI wallet (*Check Registration Certificates*, driving both `configureWrpRegistrationPolicy` and `configureIssuerRegistrationPolicy`). `RPRC_17`, `RPRC_17a` and `RPRC_21` describe wallet behaviour that therefore does not run by default; `RPRC_22a` and `RPRC_23` describe a refusal on the issuance path that likewise does not run | `EW-DM-44-019` (`RPRC_17`), `EW-DM-44-020` (`RPRC_17a`), `EW-DM-44-027` (`RPRC_21`), `AS-AP-44-005` (`RPRC_22a`), `AS-AP-44-007` (`RPRC_23`) | `ACCEPTED` — this is what makes a V0 demo feasible without an RPRC. It also means a V0 pass proves **less** than it appears to: test with the switch in both positions and report both |
| C3 | **Dev relaxations are active**: `relaxCertificateProfiles()` and `relaxPkixRevocation()` in both reference flavours, and `configureDocumentStatusResolver` uses `TrustPolicy.Action.INFORM` rather than `ENFORCE` because "the dev PID list has no revocation anchors yet" | `AS-MS-27-018` (`Reg_11`) (ETSI TS 119 411-8 profile conformance); `AS-AP-07-023` (`VCR_13`) | `INFORMATIONAL` — the reference environment is more permissive about certificate profiles and revocation than a conformant deployment. A V0 success there does not evidence profile conformance |
| C4 | **`ReaderAuthPolicy.EnforceIfPresent` admits a reader that sends no reader authentication**, while `RPA_03` requires Relying Party authentication in **all** presentation transactions | `AS-WP-06-004` (`RPA_03`) | `INFORMATIONAL` — no effect on V0: EUDIPLO always signs the request object with `x509_hash` and an `x5c`, so reader authentication is present and the chain is enforced |
| C5 | **`Preregistered` is not enabled** in the shipped build (`withClientIdSchemes(listOf(X509SanDns, X509Hash))`), though Wallet Core v0.30.2 supports it. There is no runtime escape hatch for an untrusted verifier | `AS-WP-06-005` (`RPA_04`) — the wallet is *correct* here | `ACCEPTED` — this is blocker B1. Enabling it requires editing Kotlin constants and rebuilding |
| C6 | **The dev test PID carries no age attributes.** `eu.europa.ec.eudi.pid_vc_sd_jwt` (27 claims) and `eu.europa.ec.eudi.pid_mdoc` (26 claims) at `https://issuer.eudiw.dev` contain no `age_over_18`, `age_over_NN` or `age_in_years`. This matches the current PID Rulebook rather than diverging from it | PID Rulebook v1.1, change log: "Age verification attributes removed, following CIR 2024/2977" | `INFORMATIONAL` — **not** an RI divergence; the RI is correct and the prompt's assumption is stale. Drives ADR 0005. See findings §6.3 |
| C8 | **The RP Registration Service generates the key pair server-side and delivers a PKCS#12.** The EUDI reference RP Registration Service at `https://registry.serviceproviders.eudiw.dev/` issues a Relying Party Access Certificate as a P12 containing **both** the certificate and its private key, rather than accepting a CSR for a key the Relying Party Instance generated itself. ARF §3.11.3 describes an access certificate as bound to "a key held by the Relying Party Instance", and `AS-MS-27-018` (`Reg_11`) requires Access CA issuance to comply with ETSI TS 119 411-8, whose key-management expectations assume subject-generated keys | ARF §3.11.3; `AS-MS-27-018` (`Reg_11`) | `ACCEPTED for TEST only`. A key the CA generated has been outside the subject's control by construction, so the binding ARF describes is weaker than it appears. Tolerable for a `TEST` environment whose own documentation says it "must not be used to manage real Relying Party access certificates". **Must not carry into `PRODUCTION`:** a production Access CA must accept a CSR for a key generated in the platform's key store, ideally non-exportable. Recorded against `docs/security-limitations.md` K1 |
| C7 | **EUDIPLO's recorded RI compatibility is stale.** Version tested `2026.02.26-Demo`, last verified 26 February 2026 — against current RI `2026.09.42-Demo_Build=42` (2026-09-10) and EUDIPLO v7.6.0. Noted there: the RI "forces Wallet attestation"; DC API `n/a`; ISO 18013-7 Annex C untested | — | `OPEN` — open question Q8. Until tested empirically the honest status is "unverified" |

## D. Baseline-source findings

| # | Finding | Status |
|---|---|---|
| D1 | **The Technical Specifications are not versioned by tag.** `eudi-doc-standards-and-technical-specifications` has no tags and no releases; ARF 3.0.0's `ts*.md` files are stubs linking to that repository's `main`. The ARF tag does not freeze any TS content. Each TS carries an internal version table (TS5 is at `1.5`, 20.08.2026) | `OPEN` — open question Q6. Cite *(TS internal version + commit SHA + retrieval date)*; pinned here as `ee91a294c833af5188726fd8c302c641212192aa` |
| D2 | **The PID Rulebook has also left the ARF**, to `eudi-doc-attestation-rulebooks-catalog` (likewise untagged; pinned `36f8adcf914ac06cac18d685add04e0a8a06d685`, document version 1.1). ARF 3.0.0 Annex 3.01 is a stub. The catalogue currently holds only `pid` and `mdl` | `OPEN` — same treatment as D1 |
| D3 | **There are 14 TS documents, not 12.** TS13 (`ts13-zksnarks`) and TS14 (`ts14-zkps-from-mms`) exist alongside TS4 and are all zero-knowledge-proof work. The ARF mirror renders TS13/TS14 with TS12's title, which is a defect in the mirror | `INFORMATIONAL` — the exploratory exclusion of TS4/TS13/TS14 holds |
| D4 | **None of TS1–TS14 defines the presentation profile, issuance profile, credential formats, trust anchor distribution or status mechanism.** ARF 3.0.0 delegates all five to OpenID4VP/OpenID4VCI + HAIP, ISO/IEC 18013-5 + SD-JWT VC + ETSI TS 119 472-1, ETSI TS 119 612 + TS 119 602, and the Token Status List / CIR 2024/2979 Annex 2 respectively. See findings §1.2 for the full table with HLR citations | `INFORMATIONAL` — corrects the premise of the prompt's §3.2 |
| D6 | **`OIA_08d` cites the wrong ARF section.** `EW-PIO-01-017` (`OIA_08d`) obliges a Relying Party using a redirects-based cross-device flow to "implement adequate mitigations for the challenges described in Section 4.4.3.1 of the ARF main document". In ARF 3.0.0, **§4.4.3.1 is "Introduction"** and lists no challenges; the five challenges are in **§4.4.3.2, "Challenges for remote presentation flows using custom URIs"** | `INFORMATIONAL`, **with a real consequence**: followed literally, the requirement points at a section with nothing to implement, so it would reasonably be read as vacuous. The platform derives its mitigations from §4.4.3.2 instead — [ADR 0009](adr/0009-cross-device-presentation-mitigations.md) — and `docs/traceability.md` records the cross-reference against the `OIA_08d` row |
| D7 | **ARF 3.0.0 still refers to `age_over_*` attributes that the PID Rulebook has removed.** The HLR register carries a note in Topic 3 / the data-model annexes reading "The value of the `age_over_18`, `age_over_NN`, or `age_in_years` attributes, **if present**, changes whenever the User to whom the person identification data relates has a relevant birthday." PID Rulebook v1.1 (4 Sep 2025) removed those attributes from the PID entirely — "Age verification attributes removed, following CIR 2024/2977" — and the complete current attribute set contains none of them. The live reference PID issuer advertises none either | `INFORMATIONAL` **baseline inconsistency**: residual text in the ARF implies an attribute the governing Rulebook no longer defines. The "if present" hedge makes it technically non-contradictory, but a reader taking the ARF alone would design for an attribute that does not exist — which is how this assumption reached the V0 implementation prompt. The platform follows the Rulebook: age is derived from the date of birth ([ADR 0005](adr/0005-presentation-policy-abstraction-and-minimisation-first-compilation.md) Decision 5), and the domain model is **not** bound to the PID, so a policy can target a dedicated age attestation when one exists (`tests/unit/age-not-pid-bound.test.ts`) |
| D8 | **The ETSI profile lags the ARF/CIR intermediary data model.** ARF 3.0.0 §6.6.5 makes intermediary status visible in both certificates: per the **amended** CIR 2025/848 Annex IV point 3(k) an intermediary's access certificate carries "an association to the wallet-relying party that is relying upon the intermediary" — ARF draws the consequence that an intermediary needs a separate set of access certificates per intermediated Relying Party, with a worked example of 100 Instances × 1000 customers = 100 000 certificates — and the intermediated Relying Party's registration certificate names the intermediary in `usesIntermediary`, which the Wallet Unit cross-checks against the access certificate by identifier **and Service identifier**. **ETSI TS 119 475 V1.1.1 (2025-10)**, the version ARF 3.0.0 references, read directly: `usesIntermediary` *is* profiled (Annex B.2.1 `[0..*] WalletRelyingParty` → CIR Annex I.14; Table 10 → `act.sub.id` "as specified by the intermediary WRPAC" and `act.sub.name`; `GEN-5.2.4-09`), but its Annex B mapping marks the intermediary-association row as **absent from the WRPAC** and only optional in the WRPRC, its Annex E.1 reads Annex IV point 3(k) as a "machine processable reference to the applicable certificate policy", and the phrase **"Service identifier" does not occur in the document at all** | `INFORMATIONAL`, **out of V0 scope** — V0 does not implement the intermediary profile. Recorded because it settles Phase 0 question Q7 (the prompt's assertion was right, on §6.6.5 rather than `RPI_06`) and raises Q7a. Most likely version lag, not contradiction: ETSI's normative reference is CIR 2025/848 *of 6 May 2025*, the unamended original, and its change history records V1.1.1 as the first publication (September 2025), so the same sub-point reference carries different content in each document; the Annex I point numbering drifts too (ARF cites point 16, ETSI uses 14 and 15). The ARF's own Relying Party registration discussion topic lists "adding the Relying Party Service identifier to the data model of registration certificate in ETSI TS 119 475" as a change still to be made, which corroborates the Service-identifier half. **Not checked:** the amending act's own text, and any ETSI version later than V1.1.1 |
| D5 | **Newer implementing acts are in scope than the prompt lists**: CIR (EU) 2026/1730 (TS5 v1.5 aligns to it; introduces `servedWRPServices`) and CIR (EU) 2026/1731 (amending CIR 2024/2982). Several HLRs also cite "the amended CIR 2024/2979" and "the amended CIR 2024/2982" | `OPEN` — the applicability calendar is already a gap in [`09-product-roadmap/gaps.md`](../../09-product-roadmap/gaps.md) ("Implementing-act transition"). V0 is `TEST`-only, so no applicability date is relied on |
