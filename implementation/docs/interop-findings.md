# Interoperability findings

Divergences between EUDIPLO or the EUDI Reference Implementation and ARF 3.0.0 / the Technical
Specifications, and divergences between an implementation's documentation and its code.

Per the implementation rules, a divergence is recorded here and the platform domain model is **not**
bent to match an implementation quirk.

Sources pinned as in [`phase-0-findings.md`](phase-0-findings.md) §1.

Status values: `OPEN` (unresolved), `ACCEPTED` (we work around it), `INFORMATIONAL` (no action).

---

## A. EUDIPLO v7.6.0 — documentation vs code

These matter because the adapter must be written against the code and the OpenAPI document, not
the prose.

| A9 | **The engine's initial schema comes from TypeORM synchronisation, not from its migrations — but migrations are its upgrade mechanism.** It ships **45** migrations, and `BaselineMigration1740000000000` deliberately creates nothing: on a fresh database it logs `Fresh database detected. Schema will be created by TypeORM synchronize.` / `Ensure DB_SYNCHRONIZE=true is set for initial setup.` and returns, after which every later migration skips with "table not found". With `DB_SYNCHRONIZE=false` on an empty database the engine crash-loops on `QueryFailedError: relation "client_entity" does not exist` (PostgreSQL `42P01`) from `InternalClientsProvider.onApplicationBootstrap`. `DB_SYNCHRONIZE` defaults to **true**, and its own description reads *"Set to false in production after initial setup and rely on migrations instead."* | `CONFIGURATION`, with a **two-phase lifecycle**: `true` for the first start, `false` thereafter. An earlier revision of this row said the engine "gives no alternative" — that was **overstated**, and is corrected here: synchronisation is required only for *initial creation*. Leaving it `true` is what the engine itself warns against, and on a project shipping releases weekly it is how a schema silently diverges. `docker-compose.yml` therefore defaults to `${ENGINE_DB_SYNCHRONIZE:-true}` so a first `compose up` works, and both it and `.env.example` tell the operator to flip it. Documented in [`eudiplo-integration.md`](eudiplo-integration.md); upstream issue drafted in `docs/upstream/eudiplo-baseline-migration.md`, **not filed**. Confined to the engine's own separate database (ADR 0001, ADR 0004); the platform's has no auto-synchronisation |
| A10 | **Every management route is under `/api`; the documented paths omit it.** The engine serves two OpenAPI documents on one port: the wallet-facing *Protocol API* at `/docs-json`, whose routes are unprefixed, and the *Management API* at `/api/docs-json`, whose routes are all prefixed. So the real paths are `PUT /api/session-config`, `POST /api/verifier/config`, `POST /api/verifier/offer`, `GET,DELETE /api/session/{id}`, `POST /api/key-chain/import` — while `GET /health` belongs to the protocol document and is genuinely unprefixed | **A real adapter defect, now fixed.** The adapter had the correct path only for `POST /api/oauth2/token` and `/health`, which is exactly why authentication and the health check passed while every other call returned `404`. The prefix is now applied centrally in `EngineClient.request` as `MANAGEMENT_PREFIX`, and a path that already carries it is rejected rather than silently doubled into `/api/api/...`. Caught by the adapter-contract suite the first time it ran against a real container |
| A11 | **The bootstrap `root` client cannot serve a Relying Party Instance.** Its token carries `roles: ["tenants:manage"]` and **`tenant_id: null`**: it is a tenant-*management* credential and is refused on every tenant-scoped route. A usable credential comes from `POST /api/tenant`, which returns a per-tenant admin client (`{id}-admin` plus a generated secret) whose token carries the real `tenant_id` and the `presentation:manage` / `presentation:request` roles | **A documentation defect in this repository, now fixed.** `.env.example` shipped `ENGINE_TENANT_CREDENTIALS=root=root:<secret>` as the bootstrap entry, which can never complete a presentation flow. It also **confirms ADR 0002 Decision 3 empirically**: the engine's own model requires one client per tenant, and the platform maps one engine tenant to one Relying Party Instance. Found when the adapter suite's `404`s became `401`s |
| A12 | **The presentation config's registration-certificate import field is `registrationCertImportJwt`, a *string*, and the adapter had it wrong.** The adapter sent `registrationCert: { jwt }`; `PresentationConfigCreateDto` declares `additionalProperties: false`, so the engine answers 400 `unrecognized key(s) "registrationCert"`. Worse, the engine's **own OpenAPI document** declares `registrationCertImportJwt` as `{type: "array", items: {type: "string"}}` while its zod validator rejects an array with `expected string, received array`. The engine then *stores* it as `registration_cert: { jwt }` — so the request DTO, the OpenAPI document and the stored entity all differ | **A real adapter defect, now fixed.** It was invisible because V0 holds no registration certificate, so the branch never executed — it would have failed the moment a real certificate arrived. Another instance of CLAUDE.md §6 item 10: write the adapter against the validator, not the document. Also requires an **authorised-credentials claim** in the certificate or the engine refuses it with `Registration certificate has no authorized credentials`, which is its own `RPRC_21`-style over-asking check. Covered by `tests/adapter/registration-certificate.test.ts` |
| A13 | **The engine emits the registration certificate only when a registrar is configured for the tenant.** `oid4vp.service.js` builds the claim as `verifier_info: regCert ? [{format: "registration_cert", data: regCert}] : undefined` — note `verifier_info`, the earlier OpenID4VP draft name, not `verifier_attestations` — and guards it with `if (presentationConfig.registration_cert && await this.registrarService.isEnabledForTenant(session.tenantId))`. `isEnabledForTenant` is `!!config`, and `RegistrarConfigService.saveConfig` calls `await this.authService.testCredentials(dto)` **before** saving, so the registrar must be reachable and must authenticate (an unreachable URL returns 503 and saves nothing) | **`BLOCKING` for `EW-DM-44-023` (`RPRC_19`).** Holding a valid certificate is not sufficient: through this engine at this version a registration certificate cannot reach a Wallet without a live registrar service. The platform side is complete and verified — `IntendedUse` → `RegistrationCertificate` → compiler → `VerificationPlan` → adapter → engine config — and the gap is entirely the engine's emission gate. `RPRC_19` is **not claimed**. Expect `EW-DM-44-019` (`RPRC_17`) warnings from any Wallet that checks; see [`reference-wallet-testing.md`](reference-wallet-testing.md) §8A |
| A14 | **Six engine payload shapes on the issuance side differ from what the field names and the OpenAPI document suggest.** Each was found by the adapter-contract suite against the running v7.6.0 container. (1) `usageType` for an attestation-signing key is **`attestation`** — the enum is `access \| attestation \| trustList \| statusList \| encrypt`, and the obvious guess `signing` is rejected with `Validation failed`. (2) `credentialClaims` is a **tagged union** per configuration — `{type: "inline", claims}`, `{type: "attributeProvider", …}` or `{type: "webhook", …}` — and a bare claims object is rejected with `invalid_union`. (3) `registrationCertificate` is `{enabled, mode: "import"\|"generate", jwt}`; **`enabled` is separately load-bearing** because `appendIssuerRegistrationCertificateInfo` returns early without it. (4) `authorizationServers` is a **discriminated union** on `type` (`built-in` \| `oid4vp` \| `external` \| `chained`); an entry lacking `type` is accepted by the DTO and then ignored, failing much later with `No enabled authorization server configured`. (5) The authorization-server id **`built-in` is reserved**. (6) The `/api` management prefix from A10 applies throughout | `INFORMATIONAL`, and the pattern is the point: four of the six are accepted-then-wrong rather than rejected, so a test that only asserts "the call succeeded" would have passed. All six are pinned by `tests/adapter/issuance-contract.test.ts`, which decodes what a Wallet would receive rather than trusting the configuration call |
| A15 | **EUDIPLO v7.6.0 does not produce `signed_metadata`.** The term has **zero occurrences** in the compiled source. It is the OpenID4VCI mechanism by which a Wallet authenticates the Credential Issuer metadata document itself, and the pinned Reference Wallet requires it — `configureIssuerTrust { requireSignedMetadata() }` → `IssuerMetadataPolicy.RequireSigned`. The engine *does* support the other half of the gate: `issuer_info: [{format: "registration_cert", data: jwt}]`, verified end to end | **`BLOCKING` for ARF §6.6.2.2** pre-issuance provider authentication, and therefore part of blocker B7. The platform reports it rather than implying success: `provider-authentication` returns `metadataSigned` and `walletCanAuthenticateProvider` as a conjunction, and a contract test asserts the absence so a later engine release that gains support produces a **failing test pointing at the documentation** rather than a silent change in what is claimed. Upstream issue drafted, not filed. See [`issuer-trust-model.md`](issuer-trust-model.md) gate (a) |
| A16 | **Engine tenant roles are per capability, and a tenant cannot grant its clients roles it does not itself hold.** A tenant created with `presentation:*` only gets `403 Forbidden` on `POST /api/registrar/config` and on `POST /api/client` when asked for `issuance:manage`; `PATCH /api/tenant/{id}` rejects a `roles` key outright (`unrecognized key(s) "roles"`), so the roles cannot be widened after creation | `CONFIGURATION`, and it extends A11: the engine tenant must be created **with every role the Relying Party Instance or Attestation Provider will ever need** — `presentation:manage`, `presentation:request`, `issuance:manage`, `issuance:offer`, `clients:manage`, `registrar:manage`, `tenant:admin`. Recorded in `.env.example`. A tenant provisioned too narrowly has to be recreated |
| A17 | **The engine supports PID-during-issuance natively, which is the §7.3 stretch goal.** `Oid4VpAuthorizationServerConfig` (`type: "oid4vp"`) takes a `presentationConfigId`, so the engine runs an OpenID4VP presentation *as the authorization step* of an issuance, using a presentation configuration by id | `CAPABILITY`, and it made the stretch goal a wiring decision rather than a build. The platform's `IssuancePolicyVersion.eligibilityPresentationPolicyId` selects it, and the adapter emits the `oid4vp` server instead of `built-in`. **Not yet exercised end to end**, so it is implemented and unverified — stated as such rather than counted as done |

## B. EUDIPLO vs ARF 3.0.0 / TS

| # | Finding | Citation | Status |
|---|---|---|---|
| B1 | **Revocation is reversible in EUDIPLO.** `POST /session/revoke` accepts `status: 0` (valid) after `status: 1` (revoked). ARF requires that a revocation SHALL NOT be reversed | `AS-AP-07-007` (`VCR_04`) | `OPEN` — the **platform** must reject un-revocation while still permitting reinstatement from *suspended* (`status: 2` → `0`). Enforced in the platform lifecycle, not in the engine |
| B2 | **mdoc status mechanism unverified.** ARF requires the Attestation Status List or Attestation Revocation List mechanism of Annex 2 of the amended CIR 2024/2979 for mdoc. | B3 | **Trust anchor *management* obligations are not met by caching alone.** EUDIPLO normalises ETSI TS 119 602 LoTEs and ETSI TS 119 612 Trusted Lists into one trust store and exposes cache controls, which satisfies the *shape* of `OIA_15b`. | B4 | **No signature on EUDIPLO's outbound webhooks.** Auth options are `apiKey`, `bearerToken`, `basic`, `none`; there is no payload signature, no timestamp and no event id. | B5 | **EUDIPLO persists presentation and issuance content** on the session row (`credentials: VerificationResult[]` including disclosed payloads; `credentialPayload` including inline issuance claims) for `SESSION_TTL`, default 24 h, purged by an hourly job | `AS-RP-01-002` (`OIA_16`) obliges the RP Instance to discard unique elements and timestamps as soon as they are no longer needed | `ACCEPTED` with mandatory configuration — see ADR 0004. | B8 | **`rpId` cannot be set per request.** EUDIPLO derives it automatically from the tenant's registrar relying party. | B9 | `readerAuth` (ISO 18013-7) "extracts the Access private key as a JWK, so KMS-backed non-extractable keys are not yet supported" | — | `INFORMATIONAL` — out of V0 scope (no proximity, no DC API), but it bears on any future HSM-backed deployment |

| C10 | **`POST /intended_use/create` reports success and persists nothing, which blocks Path A at the Registrar.** Observed 12 September 2026 across four attempts with different payloads. The route validates ownership correctly — a foreign id is refused with `400 "The Credential ID 1 does not belong to this user."` — and then, once ownership passes, answers `201 {"data":{"Credentials ids":[null]},"message":"Intended Use created successfully"}`. Every one of the three is unreachable | — (a defect in the reference service, not an ARF divergence) | `BLOCKING` for blocker **B1** by a second, independent cause.
